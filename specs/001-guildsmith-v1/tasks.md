## Phase 4: User Story 2 - Preview and apply structural changes from a file (Priority: P2)

**Goal**: The diff, planner, op ordering, plan hash, `plan`/`apply` and `spec_plan`/`spec_apply`.
Applying an example file to an empty server, then planning again, shows no changes (milestone
M2).

**Independent Test**: Quickstart §2–§3. Apply each example to an empty server and get exit `0`
on the re-plan; a server changed between plan and apply is refused.

## Dependencies & Execution Order

### Phase dependencies

- **Setup (1)**: no dependencies.
- **Foundational (2)**: depends on Setup and **blocks every story**.
- **US1 (3)**: depends on Foundational.
- **US2 (4)**: depends on Foundational. Its planner tests and code are independent of US1; the
  quickstart round trip (export → plan) uses US1's export.
- **US3 (5)**: depends on Foundational. T071 adds the preflight to US2's apply service, so US3 is
  finished after US2.
- **US4 (6)**: depends on Foundational. Its `bot_preflight` tool uses US3's preflight (T070), so
  that one task waits for US3.
- **US5 (7)**: depends on US3's preflight (T070).
- **US6 (8)**: depends on a working binary (any story), and is meaningful once US1–US5 are done.
- **Polish (9)**: after the chosen stories.

### Story dependency graph

```text
Setup → Foundational (incl. explain.rs) ─┬─ US1 (export) ← MVP
                                         ├─ US2 (plan/apply) ── US3 (safety, preflight) ─┬─ US5 (doctor)
                                         └─ US4 (agent tools) ··· bot_preflight task ────┘ waits for US3
                                                                       → US6 (install) → Polish
```

### Within each story

Tests first, and they must fail before implementation. Then core types and logic, then the
adapter, then app services, then MCP tools and CLI commands.
